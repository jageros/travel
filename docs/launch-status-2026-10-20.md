This run exposed an important platform boundary: GitHub requires a maintainer to authorize PR workflows created or updated using `GITHUB_TOKEN`; a successful `workflow_dispatch` run does not itself satisfy the PR's required check. See [GitHub's token behavior](https://docs.github.com/en/actions/concepts/security/github_token#when-github_token-triggers-workflow-runs) and [eligible required-check events](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#checks-from-some-workflow-jobs-are-not-evaluated). Therefore the existing token-only configuration is not yet fully unattended. A separately authorized, repository-scoped GitHub App can supply the push and PR-creation token while retaining the existing CI, approval, quota and protected-merge gates. No App or new credential was created during this acceptance run. Until that setup is completed, the remaining two approved guides can enter a release PR after quota recovery but may wait for workflow authorization before merging.
